Ce qui a change : le code est identique, mais le dossier courant change. Un chemin relatif comme murs/mur.jpg part du dossier d'ou le programme est lance. Depuis le dossier du projet, il pointe sur le bon fichier. Depuis Build/Bin/Release-Windows/chemin, il pointe sur un dossier murs qui n'existe pas, et Load rend faux avec une image vide de 0 x 0, sans message ni plantage. La panne vient donc du dossier de lancement, pas du code qui charge l'image. J'ai teste avec NkImage et non avec la salle texturee, parce que ma salle n'etait pas disponible pour cet exercice.

Ce que LocateResource essaie : elle cherche dans cet ordre, en essayant dans chaque dossier toutes les variantes du chemin avant de passer au suivant : 1. le dossier courant ; 2. le dossier de l'executable ; 3. les parents de l'executable, 8 niveaux au plus (Build/Bin/<cfg>/<App>/ est a 4 niveaux de la racine) ; 4. les parents du dossier courant, 8 niveaux au plus. Elle rend le chemin absolu trouve, ou une chaine vide, et mon code teste ce resultat avant de le donner a Load. Lance depuis le dossier du projet, le fichier est trouve des l'etape 1. Lance depuis Build/Bin/Release-Windows/chemin, murs/mur.jpg n'existe ni dans le dossier courant (etape 1) ni dans celui de l'executable (etape 2, qui est le meme dossier) ; il est trouve a l'etape 3, quatre niveaux plus haut, a la racine du projet. L'en-tete explique pourquoi cette fonction existe : le build ne copie pas les ressources a cote de l'executable.

Deja vu avec fopen : Pas tout seul. À l’exercice 1, mon programme ne trouvait pas photo.jpg et je n’ai pas tout de suite pensé au dossier de lancement ; c’est en lançant le même programme depuis deux dossiers dans cet exercice que j’ai compris que le chemin relatif part du dossier de lancement
